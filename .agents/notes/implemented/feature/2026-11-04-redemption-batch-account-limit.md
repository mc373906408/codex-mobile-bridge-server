# Agent Note: 每个账号每批兑换码限兑一次

Status: implemented

## Problem

管理员一次生成多码时，服务端只限制每个码用一次，同一账号可以连续领取同批所有码。用户要求同批每账号只兑一个并部署，以限制批量领取。现行生成事务用 `now()` 写创建时间，部署库中 51 个码属于两个时间分组，已有一条兑换，没有同账号同组重复记录。

## Decision

每次 `GenerateCodes` 创建独立 UUID 批次，所有码保存 `batch_id`；兑换记录同时保存批次，数据库 `UNIQUE(account_id,batch_id)` 和复合外键约束“同账号同批一次”及码与批次一致。现有账号行锁串行化该账号的并发兑换，批次检查在服务时间/码使用状态变更前完成，整笔事务包含审计。不同批次可叠加；同码同账号重试仍返回原回执，不增加天数；同 request ID 换码仍冲突。达到批次上限返回 409 `redemption_batch_already_used`，不消耗另一个码。

新增 `002_redemption_batches.sql` 更新当前已部署的 `001_current.sql`，不恢复此前被删除的旧开发迁移。历史码按生成事务共同的创建时间补批次，历史兑换同样计入限制；不改账号、会话、公钥、码摘要、兑换回执或已获得的服务天数。若遇已有同账号同批多条回执，唯一约束使迁移整体失败，不能删除回执或回收服务来强行通过。部署前停止旧服务以避免旧代码继续写入无批次数据。

管理员生成回执、列表和 CSV 含批次 ID，界面说明每批每账号一次；服务能力返回 `redemption_batch_limit`。桌面补充明确的中英文失败提示，服务端本身强制规则，旧客户端也不能绕过。

## Alternatives considered

- 只在界面禁止输入同批第二个码可给及时反馈，但无法约束旧客户端、其他会话及并发请求；规则放在服务端事务和数据库中。
- 按创建时间永久识别批次可以少一个字段，但时间戳不是长期业务标识，导出和排查也不明确；时间仅用于一次迁移，新批次使用 UUID。
- 给每个旧码单独分批可保留全部旧用法，但无法限制现存 51 个码，因此按当前版本真实生成事务分组；不重新生成码或变更明文。

## Consequences

同一账号无法通过换码、换会话或并发领取同批多份天数；规则限制账号而不是自然人，不阻止创建多个账号领取。批次定义为每次生成操作，重新生成是一批新的码。历史时间分组依赖已部署代码的同事务 `now()` 行为；迁移前需要检查真实库的重复领取情况。重启期间中继短暂断开，当前客户端自动重连；不会重放业务写入。旧桌面客户端收到新错误码时仍由服务端阻止兑换，友好中文提示需要加载更新后的桌面前端。
