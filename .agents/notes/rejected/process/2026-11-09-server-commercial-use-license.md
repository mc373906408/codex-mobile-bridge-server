# Agent Note: Server 商业使用许可边界

Status: rejected — 项目所有者选择 AGPLv3；禁止商业使用的待选路线不实施，结论见[AGPLv3 许可决定](../../implemented/process/2026-11-10-agplv3-license.md)。

## Problem

项目所有者提出不希望第三方商用 Server，并询问切换 AGPL 是否合适。现有 `LICENSE` 与 README 均标注 MIT，允许商业使用。AGPL 的源码提供义务也不等于禁止商业使用，直接替换许可证不能实现所述目标。

## Proposal

先明确限制的范围，再选择后续版本的许可方式；本篇记录选项，不构成已经确定或生效的新许可证。

- 若目标是让第三方修改后提供网络服务时向远程用户提供对应源码，AGPL-3.0 是候选方案，仍允许收费与商业部署。
- 若目标是允许个人或企业内部自建，但保留对外托管业务，应评估明确限制第三方托管或竞争服务的源码可见许可，并提供独立商业授权。
- 若目标是限制所有商业用途，应评估非商业使用许可与独立商业授权，明确企业内部使用是否也受限制。

禁止商业用途的许可证不符合 OSI 开源定义，项目对外描述应相应使用“源码可见”等准确术语。AGPL 加商业授权的双许可仍允许遵守 AGPL 的商业使用者选择 AGPL，不能保证所有商业用户付费。

## 已核对事实与记录归属

2026-11-09 核对本地 [LICENSE](../../../../LICENSE) 与 [README](../../../../README.md)，当前许可为 MIT。README 同时提供 `hosted` 与 `selfhost`；部署模式不改变代码许可。

检索活跃笔记中的 MIT、AGPL、license、许可证、商业与开源关键词，仅命中[全局架构记录](../../implemented/architecture/2026-11-03-server-architecture-and-scope-audit.md)的 MIT 说明。分类为部分重叠，双方互链；该记录继续描述当前状态，本篇持有待选的许可边界，没有删除或归档旧记录。

核对依据：

- [AGPL-3.0 正文](https://opensource.org/license/agpl-v3)：第 4 节允许收费分发；第 13 节要求修改后的版本向通过网络远程交互的用户提供获取对应源码的机会。该义务不等于公开所有独立系统的代码，也不禁止经营托管服务。
- [OSI 常见问题](https://opensource.org/faq)：开源软件允许商业使用，商业使用与专有软件不是同一概念。
- [OSI 开源定义](https://opensource.org/osd)：第 6 条禁止按使用领域限制授权，包括禁止用于商业活动。

## Alternatives considered

- **保留 MIT**：继续便利自部署、集成和商业采用；不能满足限制第三方商用的目标。
- **改用 AGPL-3.0**：保留标准开源许可，约束适用的修改版网络服务的源码提供义务；第三方合规收费仍被允许，因此不作为“禁止商用”的解决方案。
- **限制对外托管的源码可见许可**：更贴近保留官方托管业务的目标，也可允许企业内部自建；需要精确定义托管、竞争服务与例外，且不能称为符合 OSI 定义的开源许可。
- **非商业许可加商业授权**：可将特定商业用途保留给单独授权；限制更广，可能连企业内部自建也受限，采用和授权管理成本更高。

## Acceptance criteria

- 确定个人自用、企业内部使用、免费对外托管、收费对外托管与商业再分发的允许范围。
- 核查相关代码的著作权、贡献者授权与第三方许可证，确认能够对拟发布的新版本采用所选许可。
- 明确适用版本与生效边界；不把替换当前 `LICENSE` 表述为自动撤销已授出的旧版 MIT 权利。
- 正式选择后同步许可证、README 和发布说明；若选择 AGPL，检查适用的源码提供方式。

## Risks

“商用”边界含糊会使使用者无法判断企业自用和对外运营是否需要额外授权。过宽限制可能妨碍原本希望保留的自部署用途。

已按 MIT 合法获得旧版本的人通常仍能按该许可使用和继续维护旧代码；后续许可调整不能仅靠替换文件消除这一既有路径。本次未核查历史发布、全部贡献者和第三方代码的再授权条件，也未确定最终法律条款。
